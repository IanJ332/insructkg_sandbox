## Meaning of classifications

**EXACT REUSE** means identifiable reference code is actually used unchanged at the stated boundary. **VERIFIED FUNCTIONAL EQUIVALENCE** requires an explicit same-input behavioral comparison, scoped to the tested cases and revision. **PARTIAL IMPLEMENTATION** means some named behavior exists but the full requirement is not established. **MISSING** means the stated capability is absent in the inspected scope. **INTENTIONAL DEVIATION** means a documented scope/design difference, not equivalence. **UNVERIFIED** means evidence is insufficient. A paper-compatible interface or direction can be compatible without matching the paper's algorithm; functional equivalence requires comparative evidence; exact reproduction additionally needs the original stages, data, configurations, models and evaluation conditions. None follows merely from similar output schema. No matrix entry claims end-to-end functional equivalence or reproduction.

## Stage contracts and embeddings

Original stage chain in `reference/main.py`: ingest produces `chunks.jsonl`; LLM processing produces `mentions.jsonl` and `concept_cards.jsonl`; clustering produces `context_clusters.jsonl`; pair aggregation produces `pairpackets.jsonl`; relation judging produces `relations.jsonl`. `scripts/extract.py` lists these outputs, but presence of expected filenames or validators alone is not a successful run. Inspect stage schemas and provenance, failure handling and actual outputs before accepting an adapter. `instructkg_schema.py` is a sandbox validator, not proof it matches every revision's raw format.

The **lecture-chunk embeddings** serve cross-chunk evidence aggregation. In `reference/clustering.py`, SentenceTransformer encodes text to float32; clustering uses cosine UMAP with `random_state=42`, HDBSCAN, and representative chunks ranked against embedding centroids. Standalone CLI defaults: `all-MiniLM-L6-v2`, batch 64, 15 components and neighbors, optional clustering, dynamic min cluster size `max(5, min(25, n // 50 if n >= 500 else max(5, n // 20)))`; unspecified min samples becomes `max(1, min_cluster_size // 2)`. The orchestrator `main.py` instead defaults to batch 32, five components, minimum cluster size two and minimum contexts three; its call path sets normalized embeddings, 15 neighbors and no top-chunk limit. The paper reports normalized embeddings, 15 UMAP components and neighbors, HDBSCAN minimum cluster size 5, temperature 0.1, and H200 hardware (p. 5 §4.4; p. 12 Appendix C); orchestrator defaults therefore are not identical to that experiment. Centroid ranking in the code uses a dot product on the embeddings; normalization makes that ranking cosine-like. The paper also specifies a separate student-mapping embedding model in Appendix C; it should not be conflated with either lecture clustering or the unspecified SQL-platform attempt vectors. These are source observations, not evidence the model was cached or stages executed. Pin model revision and package/runtime versions and test representative inputs before a reproduction claim.

The **attempt embeddings** in the SQL paper are a different concern: pp. 3–4, §III.A/C say each attempt and an embedding are stored in PostgreSQL, but do not specify model, dimensions, construction, retrieval query or a demonstrated downstream vector consumer. Its described graph synchronization reads IDs and error labels (p. 4, §III.D). The backend is unavailable, so absence of a consumer cannot be proven. **UNVERIFIED**: do not invent a vector algorithm or add per-attempt embeddings until actual code or a concrete consumer, quality test and retention purpose are established.

These choices are scoped engineering decisions, not claims that SQLite reproduces either paper's architecture. Implementation should follow demonstrated requirements and tests; this decision does not itself call for a migration or new embedding system.
